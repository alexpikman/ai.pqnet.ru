# Архитектура PQlocalAgentOSv3 и перенос возможностей из v2

## Принципы

1. **v3 — самостоятельное приложение.** Код и данные v2 не изменяются. Перенос выполняется копированием выбранных доменных модулей с адаптацией контрактов.
2. **Один источник правды для оформления.** Цвета, размеры, типографика, шапка, боковая панель и отступы задаются дизайн-токенами и применяются общими компонентами ко всем страницам.
3. **Нет дублирующих разделов.** Каждая функция имеет один канонический раздел; связанные операции открываются как вкладки или действия внутри него, а не как отдельные копии.
4. **API прежде интерфейса.** Страница не считается реализованной, пока у неё нет реального backend-контракта, обработки ошибок и состояния загрузки/пустых данных.
5. **Модули изолированы.** Каждый модуль имеет manifest, версию API, входы/выходы, зависимости и явно объявленные разрешения. Загрузка исходников из GitHub не означает их автоматическое выполнение.
6. **Без неявного переноса состояния.** База данных, настройки и журналы v2 не подключаются к v3 автоматически; миграция данных оформляется отдельно и выполняется только по явному действию пользователя.

## Единая структура интерфейса

Все системные и пользовательские страницы используют общий каркас:

- боковая навигация — строится из сохранённого меню;
- шапка — заголовок, описание, хлебные крошки и действия;
- область содержимого — единая ширина, отступы и сетка;
- общие элементы — карточки, поля, таблицы, уведомления, диалоги и состояния загрузки;
- дизайн-токены — тема, акцент, фон, поверхности, границы, текст, радиус, шрифт и размеры.

Тема светлая/тёмная переключается через одну настройку `appearance.theme`. Стили компонентов не должны определять цвета независимо от токенов, кроме семантических статусов (ошибка, предупреждение, успех).

## Каталог доменов без повторения

| Канонический раздел | Ответственность | Источник для переноса из v2 |
|---|---|---|
| Рабочий стол | Сводное состояние, последние события, быстрые действия | Счётчики и системное состояние |
| Проекты | Рабочие пространства, локальные/удалённые репозитории и контекст проекта | `app/projects.py` |
| Задачи | Создание, назначение, запуск, результат и состояние выполнения | API задач и `app/agent_runtime.py` |
| AI-агенты | Реестр агентов, системные роли, назначение модели и возможностей | `app/agent_settings.py`, `app/system_agents.py` |
| Чат | Диалоги с моделью/агентом, история, настройки общения | `app/chat.py`, `app/chat_storage.py` |
| Голос | Распознавание речи и синтез ответа | `app/voice_gateway.py` |
| Модели | Доступность Ollama, список моделей, проверочный запрос | `app/model_gateway.py`, `app/model_management.py` |
| Память и знания | Память агента и задачи, просмотр и редактирование | память из `app/agent_settings.py` |
| Разрешения | Явные разрешения на файловые, системные и внешние операции | `app/permissions.py` |
| Диагностика | Проверки API, БД, файловой системы, зависимостей и локальных сервисов | `app/diagnostics.py` |
| Журнал системы | Аудит и события, фильтрация и детали события | аудит из v2 + события v3 |
| Модули | Каталог, manifest, зависимости, связи и разрешения | текущий модульный контракт v3 |
| GitHub | Подключение, поиск репозиториев, чтение/изменение файлов и коммиты | `app/github_settings.py`, `app/github_tools.py` и текущий API v3 |
| Настройки интерфейса | Тема, дизайн-токены, шапка, навигация | настройки шапки из v2 + текущие настройки v3 |

Не следует создавать отдельные страницы «История чата», «Параметры агента» или «Настройки модели», если это подфункции канонических разделов: их место — вкладки или панели соответствующего раздела.

## Порядок переноса

### Этап 1 — каркас и визуальная система
- Светлая и тёмная темы на общих токенах.
- Единая сетка и компоненты страниц.
- Проверка пользовательских страниц: они наследуют глобальное оформление автоматически.

### Этап 2 — независимые backend-домены
Переносить небольшими группами: диагностика и модели; затем агенты и разрешения; затем проекты и задачи. Для каждого домена переносится API, модели/хранилище, проверки входных данных, журналирование и тесты вместе с ним.

### Этап 3 — чат и голос
Переносить после стабилизации реестра агентов и моделей, сохраняя изоляцию истории диалогов и корректные состояния ошибок при недоступности Ollama или голосового сервиса.

### Этап 4 — интеграция и проверка
- API-контракты и регрессионные тесты;
- проверка запуска v2 и v3 одновременно на разных портах;
- отсутствие записи в каталоги и БД v2 со стороны v3;
- проверка обеих тем на каждой системной и пользовательской странице;
- проверка пустых данных, отключённых сервисов и ошибочных ответов.

## Правила качества

- Не копировать целиком `main.py` v2 в `server.py` v3: это разные серверные стеки и жизненные циклы.
- Не дублировать бизнес-логику в JavaScript и Python.
- Не добавлять фиктивные данные, декоративные действия или страницы без API.
- Не использовать массовые CSS-переопределения как замену компонентной структуре: общие значения выносить в токены, компонентные правила группировать по компонентам.
- Не переносить секреты, пользовательские данные или локальные пути из v2 в репозиторий.
- Перед каждым завершённым этапом запускать тесты backend и проверку JavaScript/CSS, а затем проверять интерфейс на локальном запуске.
