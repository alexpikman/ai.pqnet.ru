# PQlocalAgentOSv3 — полный отчёт по проекту

**Репозиторий:** https://github.com/alexpikman/PQlocalAgentOSv3  
**Основная ветка:** `main`  
**Назначение документа:** зафиксировать цели проекта, архитектуру, реализованные направления, известные ограничения и дальнейший план работ.

> Это отчёт по имеющемуся контексту проекта, истории изменений и выполненным статическим проверкам. Он не заменяет полный запуск приложения и интеграционные испытания на целевой машине. Если для конкретной функции нет подтверждения реального запуска, это отдельно отмечено.

## 1. Идея и исходные цели

PQlocalAgentOSv3 задумывается как локальная рабочая среда для управления ИИ-моделями, агентами, проектами и задачами. Это не просто чат с моделью и не обычная панель управления проектами: интерфейс должен позволять организовать работу локальных ИИ-инструментов, видеть состояние системы, управлять контекстом и расширять возможности через отдельные модули.

Основные принципы:

- **Local-first:** возможность работать с локальными провайдерами и моделями без обязательного платного API.
- **Модульность:** отдельные функциональные области и расширения должны подключаться к общей системе.
- **Единая структура интерфейса:** одинаковые паттерны страниц, списков, карточек и модальных окон.
- **Русскоязычный интерфейс:** названия действий, состояния и сообщения об ошибках должны быть понятными.
- **Постепенный перенос функций:** v3 развивается как отдельный проект; полезная логика предыдущей версии может переноситься поэтапно, без попытки скопировать старую систему целиком.
- **Безопасность и предсказуемость:** удаление и изменение сущностей не должны неожиданно уничтожать связанные данные.

## 2. Архитектура и организация кода

Проект развивается как приложение с Python-бэкендом и веб-интерфейсом. В серверной части сосредоточены API, работа с данными, провайдерами моделей, агентами, задачами и интеграциями. Клиентская часть отвечает за рабочее пространство, навигацию, формы, списки и взаимодействие с API.

В раннем плане v2 рассматривалась архитектура модульного монолита на Python/FastAPI с локальным веб-интерфейсом. Для v3 выбран самостоятельный путь развития: серверная логика и интерфейс уточняются по мере переноса и реализации функций. В текущем проектном контексте данные v3 в основном организованы через файлы в каталоге `data/`; не следует автоматически считать, что все сущности уже переведены на SQLite.

### Организация CSS

Для интерфейса закреплён принцип разделения стилей по слоям:

1. **Tokens** — переменные, размеры, цвета и общие значения.
2. **Base** — базовые правила элементов и типографики.
3. **Shell** — каркас приложения, панели и общая раскладка.
4. **Components** — отдельные UI-компоненты и кнопки.
5. **Patterns** — повторяемые паттерны, в том числе списки и карточки.
6. **Sections** — стили конкретных разделов и страниц.
7. **Responsive** — адаптация под размеры экрана.

Среди закреплённых принципов — не добавлять хаотичные переопределения в случайные файлы, не дублировать CSS для одинаковых элементов и выносить стили списков и кнопок в отдельные слои. Для списков обсуждался отдельный файл `frontend/css/list-entity.css`.

## 3. Каркас приложения и интерфейс

Основной интерфейс проектируется как рабочее пространство локальной ИИ-системы.

В требованиях и реализации интерфейса фигурируют:

- две боковые панели, которые можно скрывать;
- централизованные настройки внешнего вида;
- настройки светлой и тёмной темы;
- единые параметры отступов и компоновки заголовка страницы;
- хлебные крошки и согласованное отображение заголовка и описания раздела;
- единый подход к кнопкам, статусам, карточкам и модальным окнам;
- индикатор загрузки с анимацией логотипа PQ и сообщение при недоступности сервера;
- согласованная навигация между основными разделами;
- общие компоненты, которые можно использовать как на основной странице, так и в чате.

Настройки интерфейса должны управлять общими параметрами, а не создавать отдельные несовместимые варианты для каждой страницы. Среди обсуждавшихся значений отступов каркаса: верх — 24 px, боковой отступ страницы — 22 px, низ — 24 px, второй боковой отступ — 22 px. Эти значения следует считать целевыми настройками интерфейса, а не гарантией того, что каждый экран уже проверен визуально.

## 4. Универсальные сущности и модальные окна

Для проектов, задач, агентов и других сущностей формируется общий визуальный паттерн:

- создание и редактирование выполняется в модальном окне;
- дата создания отображается над заголовком небольшим серым текстом;
- списки не используют постоянную нумерацию строк;
- информационный значок позволяет посмотреть дату создания и полное описание;
- панели списков включают действия создания, поиска и фильтрации;
- действия редактирования и удаления располагаются единообразно;
- повторяющиеся структуры следует оформлять через общие компоненты, а не через отдельную ручную разметку для каждой страницы.

Отдельно выполнялся рефакторинг модального окна редактирования доменных сущностей и студии аватаров: логика выносилась в `frontend/domain-modal.js`, чтобы использовать её и на основной странице, и в чате. При такой архитектуре важно сохранять согласованный публичный интерфейс общего модуля и не допускать конфликтов глобальных переменных между страницами.

## 5. Провайдеры и модели

Проект предусматривает работу с локальными и облачными источниками моделей.

### Локальные провайдеры

Основные провайдеры, предусмотренные проектом:

- **Ollama** — локальный сервер моделей;
- **LM Studio** — локальный сервер с OpenAI-совместимым API;
- **OpenAI-compatible** — возможность подключать совместимые API-адреса.

Для провайдера нужны понятные настройки: имя, адрес, при необходимости API-ключ и сохранение конфигурации. В интерфейсе обсуждалось отображение числа доступных моделей рядом с провайдером.

Для списка моделей предусмотрены сведения о провайдере, имени модели и её параметрах. В частности, в интерфейсе отдельно обсуждалась замена некорректной подписи «токены» на количество параметров модели, когда такие сведения доступны из метаданных провайдера.

### Облачные модели

Для облачных источников предусмотрена отдельная вкладка и отображение имени источника, значка и способа авторизации/доступа. Конкретная работоспособность каждого облачного провайдера требует проверки с действующими настройками и ключами.

### GGUF-файлы

Отдельно исправлялась маршрутизация файловых GGUF-моделей: путь к файлу нельзя обрабатывать как URL HTTP API Ollama или облачного провайдера. Такой запрос приводил к ошибке HTTP 404.

При этом успешное направление запроса само по себе не доказывает, что инференс GGUF работает. На Windows возникала отдельная проблема загрузки `llama-cpp-python` — ошибка загрузки `llama.dll` или её зависимости. Полноценный запуск GGUF-модели на целевой машине требует отдельного подтверждения после исправления окружения.

## 6. Чат и работа с агентами

В проекте предусмотрена отдельная страница чата с собственными клиентскими файлами, выбором модели, историей сообщений, состояниями ожидания и отображением ошибок. Обсуждалась отправка полной истории диалога на сервер через API чата, а также очистка истории и отображение ответа модели без использования всплывающих alert-окон.

В общей системе агентам отводится отдельная роль: агент должен работать с выбранной моделью, контекстом проекта и доступными инструментами. Дальнейшее развитие предполагает отдельные разговоры и задачи для агентов, а также возможность редактировать их настройки через общее модальное окно.

**Ограничение проверки:** наличие API и клиентской логики не означает, что реальный ответ Ollama, переключение всех моделей и полный цикл работы каждого агента проверены в работающем браузере. Эти сценарии необходимо тестировать на локальном сервере.

## 7. Проекты, задачи и память проекта

Проекты служат контейнерами для рабочего контекста и связанных задач. Для них развиваются список, редактирование, настройки среды и память проекта.

Среди требований к интерфейсу проекта:

- возможность загружать логотип проекта;
- отображение логотипа слева в карточке проекта, ориентировочный размер — 80 × 80 px;
- отдельная кнопка перехода к памяти проекта;
- навигация по сводке, ограничениям, задачам, агентам и другим разделам памяти;
- действия сохранения и очистки памяти в верхней правой части;
- согласованное отображение количества элементов в разделах.

Очистка памяти и удаление самого проекта — разные операции и должны иметь отдельные подтверждения.

### Защита связанных задач при удалении проекта

В серверной обработке удаления проекта добавлена проверка связанных задач. Если задачи ссылаются на проект через `project_id` или `projectId`, сервер должен отклонить удаление с HTTP 409 и сообщением:

> Нельзя удалить проект, к которому привязаны задачи. Сначала удалите или переназначьте задачи

Это правило защищает от случайного нарушения связей. Полное поведение следует подтвердить интеграционным тестом на реально запущенном сервере.

### Удаление проекта из чата

В чате действие для проекта изменено на «Убрать из чата». Оно должно отвязывать проект от локального рабочего пространства чата, а не вызывать серверное удаление глобального проекта. Обновляются локальный список проектов, ссылки проекта в разговорах и активный проект, после чего сохраняется состояние рабочего пространства.

## 8. Типы среды проекта: local, github, ssh

Для проекта введено направление настройки типа среды:

- `local` — локальная среда;
- `github` — работа с репозиторием GitHub;
- `ssh` — работа через SSH-подключение.

Для этих вариантов развивались серверная модель проекта, инструкции для агента и условные поля в модальном окне. Старые проекты должны получать тип `local` по умолчанию, чтобы отсутствие нового поля не ломало существующие данные.

Для SSH-среды агенту и запуску задачи передаются сведения о выбранном подключении и рабочем каталоге. Команды должны начинаться с перехода в настроенный рабочий каталог с корректным экранированием пути.

**Важное ограничение безопасности:** заданный `working_dir` определяет начальный каталог команды, но сам по себе не является песочницей. Если запускаемый процесс имеет права на другие каталоги, произвольная команда может выйти за пределы указанной папки. Для изоляции нужны дополнительные системные ограничения.

**Оставшаяся зона проверки:** сценарии GitHub-среды требуют подтверждения того, что все инструменты действительно используют репозиторий конкретного проекта, а не глобальную настройку репозитория. Это необходимо проверить реальными задачами.

## 9. SSH-подключения и инструменты агента

В проект добавлялись серверная поддержка SSH-подключений, хранение параметров подключения, API, идентификаторы подключений в контексте агента и элементы интерфейса для управления подключениями и правами.

Для удалённых команд использовалась библиотека Paramiko, добавленная в зависимости. При работе с URL и сетевыми инструментами также учитывалась защита от SSRF — нежелательных запросов к внутренним адресам и сервисам.

Наличие SSH-формы и серверных обработчиков не подтверждает успешное подключение к каждому реальному серверу. Проверить необходимо как минимум сохранение параметров, проверку соединения, выполнение команды в нужном каталоге, обработку тайм-аутов и отказов, а также соблюдение выбранных разрешений.

## 10. Диагностика и телеметрия

Диагностика и телеметрия предназначены для отображения состояния сервера и аппаратных ресурсов. В предыдущих требованиях подробно перечислялись показатели CPU, логических ядер и другие параметры системы, с обязательным отображением в интерфейсе и предоставлением данных через API.

В процессе разработки исправлялись обновление диагностических показателей, структура строк сущностей и отображение статусов. Отдельно рассматривалась задержка обновления из-за серверного кеширования: частые запросы клиента не обязательно приводят к столь же частому обновлению показателей на экране, если сервер возвращает кешированные данные.

Для дальнейшей стабилизации следует составить перечень всех поддерживаемых телеметрических параметров и для каждого проверить:
1. источник и единицы измерения;
2. корректность значения и поведение при отсутствии данных;
3. API-поле и формат ответа;
4. визуализацию на странице;
5. частоту обновления и влияние кеша.

Нельзя считать полный набор метрик готовым только на основании наличия страницы диагностики: необходима сверка всех параметров с фактическим API и визуальным интерфейсом.

## 11. GitHub и управление репозиторием

В настройках и интеграциях развивалась поддержка GitHub: токен, имя подключения, срок действия, URL репозитория, рабочая директория, методы API, проверка доступа и журналы операций.

Для токена на Windows отдельно исправлялась проблема шифрования с использованием DPAPI. При ошибке шифрования важно корректно работать с типами `ctypes`, структурами `DATA_BLOB`, указателями и освобождением выделенной Windows памятью. Сообщение «Не удалось зашифровать токен» нельзя считать устранённым без проверки на реальной Windows-системе с сохранением и повторным чтением подключения.

Сохранение токена и его использование — отдельные проверки: после сохранения нужно убедиться, что токен не отображается в открытом виде, а тест доступа к GitHub проходит с корректными правами.

## 12. Расширяемость и модули

Одно из долгосрочных требований — возможность добавлять модули в общий каталог и подключать их к единой структуре приложения. Предусматривались конструктор меню, настройка интерфейсной темы и поиск универсальных модулей, в том числе из GitHub.

Для загрузки сторонних модулей важны ограничения: нельзя автоматически исполнять произвольный код только потому, что он скачан из репозитория. В проектном описании упоминались ограничения на объём загрузки и число текстовых файлов, а также отказ от автоматического исполнения загруженного содержимого. Эти ограничения следует сохранить и подтвердить тестами при реализации установщика модулей.

Также обсуждался графовый исполнитель с операциями `input`, `template`, `ollama`, `transform` и `output`. Графовый сценарий должен валидироваться, а ошибки узлов — возвращаться в понятном формате. Для каждого узла необходимы проверки входных данных, тайм-аутов и ошибок провайдера.

## 13. Интеграции и локальные инструменты

В план развития входили интеграции с локальными инструментами, включая ComfyUI, а также работа с локальными моделями и агентами. Для локального ИИ важны не только наличие URL или поля настройки, но и диагностика доступности, корректное отображение состояния и понятная ошибка при отсутствии сервиса.

Поддержка интеграции должна включать проверку соединения, описание доступных операций, обработку ошибок и контроль того, какие действия агенту разрешены. Успешная работа одного локального инструмента не доказывает работоспособность всех интеграций.

## 14. Проверки и достоверность текущего статуса

В истории разработки упоминались проверки синтаксиса Python и JavaScript, проверка JSON и отдельные unit-тесты через GitHub Actions. Для некоторых последних правок также выполнялись статические проверки содержимого файлов: наличие ожидаемых строк, отсутствие старого HTTP-вызова в обработчике чата, наличие сохранения рабочего пространства и корректного ответа 409 при удалении связанного проекта.

При этом для последних изменений с отвязкой проекта от чата и защитой удаления проекта не заявлялся полноценный запуск приложения в браузере. Не подтверждены только статической проверкой:

- визуальное поведение всех страниц после последних изменений;
- реальные запросы к API на работающем сервере;

PQlocalAgentOSv3 развивается как самостоятельная локальная среда для управления моделями, агентами, проектами и задачами.
