00 / MISSION & SCOPE

Назначение платформы и границы ядра

PQlocalAgentOS — модульная платформа управления ИИ-агентами, предназначенная для проектирования, создания, запуска и непрерывного совершенствования интеллектуальных систем и автоматизированных процессов. Она объединяет облачные и локальные модели, координирует коллективную работу агентов и предоставляет контролируемые механизмы расширения. Сейчас цель — определить ядро платформы и подготовить локальную версию для Windows 11.

CORE PLATFORM

Ядро платформы

Реестр агентов и ролей, шлюз моделей, диспетчер задач, workflow-планы с зависимостями, ограниченный контекст/память, библиотека результатов, настройки, хранилище, безопасность, аудит и мониторинг.

FUTURE EXTENSIONS

Отдельные будущие расширения

Среда работы с пользовательскими проектами: SSH, Git/code review, файлы, команды, тесты, сборка, развёртывание и база знаний проекта. Эти возможности не смешиваются с обязательным ядром MVP и вынесены в раздел «Модули».

Контролируемое самообновление: в будущем ИИ может предложить патч, применить его только к изолированной копии, запустить проверки и показать diff. Изменение основной версии — только после подтверждения пользователя; необходимы резервная копия и откат.
02 / ARCHITECTURE

Концепция и архитектура

Граница MVP: реальный backend и UI для задач/агентов/моделей, SQLite, журнал, ошибки и безопасная конфигурация. Модульная среда для управления существующими проектами, автоматический запуск команд и самоизменение кода не входят в ядро первой версии.

PQlocalAgentOS — локально запускаемое приложение для управления командой ИИ-агентов, а не замена Windows и не среда разработки всех пользовательских проектов. Ядро отвечает за модели, агентов, задачи, планы, память/контекст, результаты, безопасность и наблюдаемость. Инструменты управления чужими проектами (SSH, Git, сборка и развёртывание) — отдельные будущие расширения.

инференс модели

REST API

Маршруты health, tasks, agents, models, settings и audit. Контракты запросов/ответов описываются в docs/api-contract.md; ошибки возвращаются в едином формате.

Оркестратор

Создаёт задачу, определяет последовательность ролей, хранит статусы и собирает результат. Оркестрация — отдельная серверная логика, а не только анимация на экране.

Хранилище

Настройки, агенты, журнал и состояние задач должны переживать перезапуск. Для рабочего приложения предпочтительно серверное хранилище; браузерное localStorage годится для локальных предпочтений.

Роли и ответственность

COORDINATION

MANAGER

Принимает цель, декомпозирует задачу, назначает этапы, следит за статусами и собирает итог.

DESIGN

Проектирует структуру, UX/UI, состояния экранов и визуальные компоненты.

IMPLEMENTATION

Пишет код и предлагает изменения в пределах явно предоставленных прав.

Назначения ролей описывают целевую логику. Чтобы агенты действительно взаимодействовали, нужно реализовать диспетчеризацию, контекст задач, формат результатов, правила повторных попыток и передачу управления.

OBSERVABILITY

Мониторинг и метрики

Проверка сервисов, времени ответа, ошибок, токенов, очередей, дискового пространства и сбор диагностического пакета для поддержки.

INTEGRATIONS

Внешние интеграции

Issue tracker, CI/CD, уведомления, webhooks и календарь задач через отдельные коннекторы. Секреты — в системном хранилище/переменных окружения, не в manifest.

Контракт модуля

  • Manifest: уникальный ID, имя, версия, совместимость API, точка входа и описание.
  • Permissions: минимально необходимые разрешения — например, remote.connect, filesystem.scoped, command.allowlist.
  • Lifecycle: обнаружен → проверен → настроен → включён → остановлен/отключён; ошибка должна быть видна в журнале.
  • Надёжность: таймауты, отмена, ограничение ресурсов, идемпотентность и корректная обработка частичного сбоя.
  • Безопасность: подтверждение опасных действий, область файловой системы, allowlist команд, журнал аудита и отсутствие автоматического исполнения неизвестного кода.
  • Тестирование: модульный тест, контрактный тест API и dry-run до выполнения операций с побочными эффектами.
Ключевая граница: включение модуля в интерфейсе не означает, что он установлен или уже подключился. Реальный статус должен подтверждаться backend-проверкой.

08 / SECURITY & DATA

Безопасность и сохранность данных

Локальные секреты

Хранить чувствительные значения отдельно от кода, ограничить доступ к каталогу secrets средствами Windows, не записывать токены и пароли в логи и исключить секреты из Git.

Права агента

Разделять чтение и изменение файлов. Ограничивать рабочие каталоги, проверять пути, журналировать действия и запрашивать подтверждение перед удалением или запуском потенциально опасных команд.

Сетевая поверхность

Для локального использования привязывать backend к 127.0.0.1. Не открывать интерфейс в локальную сеть или интернет без отдельной модели аутентификации и защиты.

Офлайн-проверка

Локальная архитектура уменьшает зависимость от облака, но офлайн-режим подтверждается только проверкой сетевых обращений и заранее загруженных зависимостей.

Обязательное правило: не запускать агента с правами администратора по умолчанию. Не разрешать модели бесконтрольно выполнять команды или изменять произвольные файлы.
09 / DEFINITION OF DONE

Критерии готовности первой версии

  • Приложение запускается локально повторяемой командой и сообщает понятные ошибки.
  • Интерфейс выполнен в едином стиле; в пользовательском интерфейсе нет эмодзи.
  • Список моделей формируется по фактическому ответу runtime, а не по демонстрационным значениям.
  • Пользовательский запрос доходит до модели через backend и отображает реальный ответ.
  • Статусы, сообщения и этапы задачи отражают реальные события системы.
  • Настройки и конфигурации сохраняются после перезапуска.
  • Действия агентов ограничены правами, а ошибки и важные операции журналируются.
  • Есть базовые тесты API, подключения модели и основного сценария задачи.
!

Честно о статусе

Проект находится в альфа-стадии. Это значит: интерфейс и API могут меняться, часть сценариев ещё не завершена, а документация обновляется по мере развития. Если вам нужен стабильный production-инструмент «прямо сейчас» — посмотрите на зрелые альтернативы. Если вам интересен локальный контроль над агентами с открытым кодом — проект стоит изучения.

Границы, заявленные разработчиками: не универсальный адаптер всех провайдеров; не многопользовательский production-сервис; без заявленного sandbox для инструментов.

Обзор проекта

PQlocalAgentOSv3 — локальное приложение для настройки AI-агентов, проектов, модулей и интерфейса. Сервер запускается в Windows через start.bat и по умолчанию слушает 127.0.0.1:8765. Это альфа: наличие интерфейса или API ещё не означает, что все сценарии завершены.

Цель

Создать локальную среду, в которой пользователь управляет агентами, проектами, моделями, модулями и интерфейсом, а ход чат-агента представлен последовательностью наблюдаемых событий.

Границы и не-цели

  • Не универсальный адаптер всех провайдеров: потоковый чат отклоняется, если формат провайдера не Ollama.
  • Не многопользовательский production-сервис.
  • Без заявленного sandbox для инструментов и полной мультимодальности.
